# Design

## Context

Обычный и упрощённый POST используют общий сериализатор с четырьмя обязательными полями. Обновление идёт через отдельный DTO и сервис, который загружает заявку до записи. Ответы строятся отдельными DTO в `showcase` и `teams`. Требования описаны в [proposal.md](proposal.md) и [спецификации](specs/application-kinds/spec.md).

## Goals / Non-Goals

**Goals**

- Сохранить обратную совместимость создания без указания типа и обычных частичных обновлений.
- Обеспечить одинаковые значения полей во всех представлениях одной заявки.

**Non-Goals**

- Изменение интерфейса фронтенда, формата Excel, фильтров и агрегатов по внутренним и внешним заказчикам.

## Decisions

1. Хранить тип и описание на `ProjectApplication`. Использовать Django `TextChoices` для `project` / `case`, непустой в смысле `NOT NULL` столбец с default `project` и текстовый столбец с default `""`. Отдельная модель кейса потребовала бы менять связи с треками и командами, хотя идентификатор заявки сохраняется.
2. Передавать оба поля через сериализаторы, DTO и репозиторий. Сериализатор проверяет форму значений, включая допустимый тип, а правила обязательности учитывают тип и операцию. Для существующих путей создания внутри сервиса сохранить различия их текущих проверок. При PUT/PATCH использовать переданный тип либо сохранённый. Для перехода вычислять набор обязательных полей из сохранённой заявки и входящих изменений. При обновлении обычной заявки без смены типа сохранить текущую проверку только переданных полей. Вычисление только из тела PATCH сделало бы проверку неполной.
3. Записывать только явно переданные изменения, включая допустимые пустые строки. Передача одного типа сохраняет все остальные значения. Для админской формы применить те же условия обязательности, учитывая, что модель должна позволять пустые поля обычной формы у кейса.
4. Добавить пару полей в сериализацию каждого способа выдачи заявки. Использовать snake_case для основного API заявок, списка проектов и детальной студенческой витрины, camelCase для списка витрины, результатов записи на проект и вложенных снимков команд и групп. Для смешанных DTO треков и статистики применять соглашение их конкретного представления и закрепить ключи в контрактных тестах. Возвращать строки из уже загруженного объекта, сохраняя существующее `null` для отсутствующего вложенного проекта. Чистые ссылки по ID, агрегаты, логи и ответы без объекта заявки не требуют пары полей.

## Risks / Trade-offs

- Длинное описание увеличивает объём списков и вложенных выдач → возвращать полный сохранённый текст согласно общему контракту и использовать существующие выборки.
- Новое чтение полей на объектах из `only()`, `defer()` или `values()` может создать дополнительные запросы → включить поля в такие проекции и проверить ограничение числа запросов в статистике.
- Выдача текста в кратких карточках наследует доступ к соответствующему проекту → сохранить область выборки и проверить доступ на публичных и ролевых маршрутах.

## Migration Plan

Применить аддитивную миграцию перед запуском версии, которая читает новые поля. Старые записи получат `project` и пустую строку без изменения их содержимого. При откате приложения сохранить добавленные столбцы и данные кейсов. Удаление столбцов потребует отдельного решения по сохранённым данным.
