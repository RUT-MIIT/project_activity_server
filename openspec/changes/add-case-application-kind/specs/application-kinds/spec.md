# Spec Delta

## Purpose

Поддержка обычных проектных заявок и заявок-кейсов с разными обязательными полями и единым контрактом выдачи.

## ADDED Requirements

### Requirement: Тип заявки и значения по умолчанию

Система SHALL хранить тип заявки `application_kind` со значением `project` или `case` и текстовое поле `case_description` («Кейс»). Для существующих записей и при создании без указания типа система SHALL использовать `project`. Отсутствующий текст кейса SHALL представляться пустой строкой.

#### Scenario: Существующая заявка и прежний клиент

- **WHEN** клиент читает существующую заявку или создаёт обычную заявку без новых полей
- **THEN** API возвращает тип `project` и пустое описание кейса, сохраняя ранее доступные данные

#### Scenario: Неизвестный тип

- **WHEN** клиент явно передаёт тип, отличный от `project` и `case`
- **THEN** API возвращает HTTP 400 с ошибкой поля типа и сохраняет прежнее состояние записи

### Requirement: Валидация по типу заявки

Система SHALL требовать для `case` непустой после удаления крайних пробелов `case_description`. Для этого типа `problem_holder`, `goal`, `barrier` и `existing_solutions` SHALL допускать отсутствие и пустые значения. Для `project` SHALL действовать существующие правила соответствующей операции, а описание кейса SHALL быть необязательным.

#### Scenario: Создание заявки-кейса

- **WHEN** клиент отправляет корректные общие данные и непустой текст кейса в обычную или упрощённую форму создания
- **THEN** API создаёт заявку типа `case`, даже если четыре поля обычной заявки отсутствуют или пусты

#### Scenario: Кейс без текста

- **WHEN** клиент создаёт заявку-кейс без текста или обновлением приводит её описание к пустому значению
- **THEN** API возвращает HTTP 400 с ошибкой `case_description`

#### Scenario: Смена типа с неполными данными

- **WHEN** клиент меняет тип, а сохранённые и переданные вместе поля не удовлетворяют требованиям нового типа
- **THEN** API отклоняет обновление с ошибками соответствующих полей

### Requirement: Сохранение полей при переключении

Система SHALL сохранять все явно не изменённые поля при переключении типа в обоих направлениях. При обновлении без поля типа SHALL применяться сохранённый тип. Клиент выбирает отображаемые поля.

#### Scenario: Переключение туда и обратно

- **WHEN** клиент сохраняет кейс для существующей обычной заявки, затем меняет тип обратно, не передавая четыре поля обычной формы повторно
- **THEN** четыре сохранённых значения доступны для валидации и выдачи, а описание кейса сохраняется

### Requirement: Выдача типа и кейса во всех представлениях заявки

Система SHALL возвращать оба поля для каждого представления заявки или проекта, включая списки, детали, ответы действий и краткие вложенные объекты. Имена SHALL соответствовать контракту конкретного представления: `application_kind` и `case_description` либо `applicationKind` и `caseDescription`. Существующие поля, включая внутренний/внешний тип, SHALL сохранять имена и смысл. Система SHALL применять действующие права доступа и возвращать фактически сохранённые значения.

#### Scenario: Основная выдача и смежные API

- **WHEN** клиент получает заявку в API заявок, проектов, треков, студенческой витрине, витрине наставника, статистике или в кратком представлении выбранного проекта команды, группы либо студента
- **THEN** объект содержит значение типа и описание кейса, включая пустую строку при отсутствии текста

#### Scenario: Выдача после смены типа

- **WHEN** клиент получает обычную заявку с ранее сохранённым текстом кейса или кейс с ранее сохранёнными полями обычной заявки
- **THEN** оба новых поля и присутствующие в этом представлении старые поля возвращают сохранённые значения независимо от выбранного типа
