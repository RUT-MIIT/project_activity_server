# Design

## Context

`is_internal_customer` хранится в модели и используется в DTO, dashboard и статистике проектов. `is_external` независимо влияет на маршрут упрощённой заявки и разрешения. Предыдущее изменение `add-case-application-kind` уже расширило вложенные DTO и не архивировано; оно даёт карту всех представлений. Существующая спецификация students-stats говорит не менять операционный список, а проект уже добавил в его вложенные проекты поля вида заявки: здесь требуется только аддитивное поле внутри проекта, без переименования или удаления старых полей.

## Goals / Non-Goals

**Goals:** Один трёхзначный источник истины, миграция без догадок, совместимость старых клиентов и согласованная аналитика.

**Non-Goals:** Изменение маршрутов согласования, восстановление исторических представителей по неявным признакам или переопределение `application_kind`.

## Decisions

- Добавить поле choices и миграцией перенести boolean до удаления или преобразования старого столбца. Вычислять `is_internal_customer` из нового типа в API и модели; проверить все ORM-фильтры и внутренние записи, поскольку property не работает в SQL-фильтрах. Альтернатива с двумя независимыми полями рискует рассинхронизацией.
- Сохранять старый входной boolean через нормализацию на границе create/PATCH. При обоих полях сравнивать булеву проекцию; противоречие — 400. Явный старый `false` устанавливает `external`, поэтому старый клиент может поменять `representative`; операция без обоих полей тип не меняет.
- В dashboard фильтр `external` выбирает точный тип, `representative` — отдельный; метрика доли внешних агрегирует оба. Поле `type` статистики содержит точный тип; предусмотреть обновление клиентов с закрытым enum.
- Везде, где уже выдаются `application_kind`/`applicationKind`, распространить соответствующий `customer_type`/`customerType`; также проверить прочие представления заявки. Применять прежние права и избегать N+1 и `only()` без нового поля.
- Импорт Excel сохраняет прежнее сопоставление «внутренний»/«внешний» и прежний маршрут `is_external`; пустое значение отображается в `external` по прежнему булевому значению. Новый вариант источника не выдумывать.

## Risks / Trade-offs

- [Старый клиент явно отправляет false при редактировании представителя] → документировать изменение типа, добавить тест и рекомендовать клиентам отправлять `customer_type`.
- [Отдельное поле в большом числе DTO или отложенная загрузка] → пройти пути showcase/accounts/teams и покрыть тестами выдачу и число запросов.
- [Изменение двухкатегорийных enum у клиентов] → документировать новое значение и различие фильтра и метрики; без обновления клиентов возможны ошибки отображения.
- [Откат миграции после появления `representative`] → в boolean останется только `false`; восстановить различие невозможно, поэтому перед откатом требуется сохранить данные и проверить согласованность схемы и кода.

## Migration Plan

Развернуть миграцию и совместимый код вместе; проверить распределение старых значений и три типа через API и dashboard. При откате предварительно сохранить значения `customer_type`; обратное отображение в boolean сводит `representative` и `external` к `false`.
