# Spec Delta

## Purpose

Сохранять и предоставлять три типа заказчика заявки, включая внешнего заказчика, работающего через представителя института.

## ADDED Requirements

### Requirement: Тип заказчика и миграция
Система SHALL хранить `customer_type` со значениями `internal`, `representative` или `external` как источник истины. При миграции `is_internal_customer=true` SHALL преобразовываться в `internal`, а `false` — в `external`. При создании без обоих полей SHALL использоваться `external`.

#### Scenario: Существующие записи
- **WHEN** миграция применяется к заявкам с прежним boolean
- **THEN** значения `true` и `false` становятся соответственно `internal` и `external`; ни одна старая запись не становится `representative` по догадке

### Requirement: Создание, обновление и совместимость
Обычный и упрощённый POST и PATCH заявки SHALL принимать `customer_type`. Отсутствие поля в PATCH SHALL сохранять текущее значение, если не передан старый boolean. Неизвестные значения SHALL отклоняться с HTTP 400. Для обратной совместимости `is_internal_customer` SHALL выводиться как `customer_type == internal`; при записи одного только старого поля `true` SHALL означать `internal`, `false` — `external`. Если оба поля переданы и противоречат друг другу, запрос SHALL отклоняться с HTTP 400.

#### Scenario: Представитель переживает изменение других полей
- **WHEN** заявка создана с `customer_type=representative` и затем изменена PATCH без обоих полей типа
- **THEN** сохраняется `representative`, а `is_internal_customer` в ответе равен `false`

#### Scenario: Несогласованные поля
- **WHEN** клиент передаёт `customer_type=representative` и `is_internal_customer=true`
- **THEN** сервер возвращает HTTP 400 без изменения заявки

#### Scenario: Старый клиент
- **WHEN** старый клиент создаёт заявку или явно меняет её через `is_internal_customer=false` без `customer_type`
- **THEN** сохраняется тип `external`

### Requirement: Тип заказчика во всех представлениях
Все представления заявки или проекта, включая создание, детали, списки, вложенные объекты, витрины, треки, команды, группы, статистику и проекты авторов, SHALL включать сохранённый тип под именем `customer_type` или `customerType` согласно регистру конкретного API. При отсутствии связанной заявки прежние правила `null` SHALL сохраняться. Существующие поля, права доступа и правила видимости SHALL сохраняться.

#### Scenario: Разные представления одной заявки
- **WHEN** клиент получает заявку `representative` через основной API и camelCase-представление проекта
- **THEN** ответы содержат соответственно `customer_type: representative` и `customerType: representative`

### Requirement: Три типа в аналитике
Фильтр dashboard `application_type` SHALL принимать `all`, `internal`, `external`, `representative`; отдельные типы SHALL выбирать только точное совпадение. Распределение по типам SHALL включать три отдельные категории. Показатель доли внешних SHALL считать внешними оба типа `external` и `representative`. Поле `type` в статистике проектов SHALL возвращать фактический трёхзначный тип.

#### Scenario: Фильтрация представителя
- **WHEN** dashboard запрашивается с `application_type=representative`
- **THEN** в расчётах участвуют только заявки этого типа

#### Scenario: Доля и разбивка
- **WHEN** доступны по одной заявке каждого типа
- **THEN** распределение показывает три категории по одной заявке, а доля внешних составляет две из трёх

### Requirement: Независимость маршрута заявки
Признак `is_external` SHALL сохранять действующее значение и смысл маршрута создания и согласования независимо от `customer_type`. Смена типа заказчика SHALL NOT автоматически менять статус, права или `is_external`.

#### Scenario: Упрощённое создание
- **WHEN** заявка создана через `simple` с `customer_type=internal`
- **THEN** тип заказчика равен `internal`, а существующие правила внешнего маршрута упрощённой заявки сохраняются
