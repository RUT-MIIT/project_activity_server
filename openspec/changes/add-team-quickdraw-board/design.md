# Design

## Context

Оба существующих представления «Моя команда» используют `TeamSemester.id`. REST смонтирован под `/api/teams/` и использует SimpleJWT. Деплой запускает Gunicorn для WSGI, а `config/asgi.py` пока обслуживает только HTTP.

## Goals / Non-Goals

- Одна доска на команду, общий контроль доступа для REST и WebSocket, непрозрачные данные Quickdraw.
- Границы MVP описаны в proposal. Сокет доставляет текущие события, а БД хранит последний успешно записанный снимок.

## Decisions

1. `TeamBoard` с `OneToOneField` на `TeamSemester`, каскадным удалением и `JSONField`. Уникальность в БД защищает от создания двух строк при параллельном первом PUT. Атомарная запись целого объекта обеспечивает семантику «последняя запись побеждает». Привязка к базовому `Team` могла бы объединить разные составы команды.
2. Для REST переиспользовать выбор семестра и проверку студента из `my-team`, а членство определять по записи участника. Сокет авторизовать через SimpleJWT и проверять членство по точному ID из URL до принятия подключения. Для браузера проверять Origin по отдельному списку настроек. Вариант авторизации первым сообщением потребовал бы дополнительного состояния протокола до первого snapshot.
3. Подписывать сокет на группу Channels до чтения snapshot, чтобы события, доставленные после подписки, обрабатывались после первого сообщения. Хранить отправителя во внутреннем событии как имя канала. Redis обеспечивает доставку между процессами. Snapshot и `hello` обслуживаются напрямую, без передачи через Redis. Проверять формат конверта `diff` и ограничивать его размер с учётом ограничения channel layer. Содержимое записей остаётся непрозрачным.
4. PUT принимает JSON, ограничивает чтение тела 8 МиБ и возвращает 413 до записи. Согласовать лимит Django и прокси для этого пути, включая запросы без доверенного Content-Length. Полный snapshot сохраняется через REST после паузы на фронте. Запись через WebSocket или серверное слияние правок усложнили бы первый релиз.
5. На фронте использовать один и тот же контекст семестра для REST и WS. Первый серверный snapshot загружать до отправки локальных правок и применять входящие diff как remote в порядке доставки. Автоматический `hello` при connect убрать, чтобы повторная загрузка не затёрла текущие правки. При отсутствии команды оставить локальную доску. Путь к клиентскому репозиторию в текущем workspace не найден, изменения фронта выполняются отдельно.

## Risks / Trade-offs

- Правка, разосланная до подключения новичка и ещё не записанная в БД, может отсутствовать у него до следующей загрузки snapshot. Журнал событий и воспроизведение пропущенных изменений выходят за пределы MVP.
- Параллельные или устаревшие PUT могут перезаписать предыдущий снимок. Клиенту следует держать один PUT в полёте на вкладку и сохранять актуальное общее состояние, включая применённые remote-правки.
- JWT передаётся в query string. Использовать WSS и исключить query string из журналов сокета на прокси и ASGI-сервере. Изменение состава после открытия сокета требует явной стратегии. Для MVP проверять право при каждом новом подключении, при необходимости немедленного отзыва отдельно добавить отключение открытых соединений.

## Migration Plan

Применить миграцию, настроить Redis и разрешённые Origin, поднять отдельный ASGI-процесс и направить на него `/ws/` с заголовками Upgrade/Connection. Сохранить существующий HTTP-процесс и проверить лимит PUT через прокси. После проверки включить клиентский транспорт. При откате отключить новый транспорт и маршрут, сохранив таблицу для повторного запуска.
