# Design

## Context

`UserManagementPermission` и `UserManagementDomain` сейчас допускают запись только для admin, cpds и staff. Сервис получает цель через список, ограниченный подразделениями; сериализатор принимает роль, подразделение, email и телефон. Общая функция доступа поднимается до корня дерева, который может находиться выше подразделения института. См. proposal и спецификацию для границ изменения.

## Goals / Non-Goals

**Goals:** Проверять права на объект, поля и итоговые значения на сервере до записи; сохранить существующее API и права прежних участников.

**Non-Goals:** Изменение модели ролей, регистрация пользователей, расширение прав чтения или изменение общего определения доступа для других функций.

## Decisions

- Разрешить действие PATCH на уровне permission, затем централизованно проверять полномочия конкретного ответственного в сервисе/домене до вызова репозитория. Одного расширения списка ролей недостаточно: оно разрешило бы все поля и роли.
- Для записи строить множество подразделений от подразделения каждого доступного активного института вниз, без подъёма к общему корню. Текущее и целевое подразделение должны принадлежать одному доступному институту. Не менять общий helper глобально, чтобы не изменять другие API и существующее чтение.
- Явно ограничить изменяемые поля и защищённые роли как цели, так и нового значения; переданные ответственным института email и phone игнорировать до валидации и сохранения. Отдельно учитывать `is_staff` и запрет изменения собственной защищённой учётной записи.
- Рассчитывать итоговую роль и подразделение с учётом отсутствующих полей и корректного имени `department_id`; текущая проверка домена использует `department`, хотя сервис передаёт `department_id`. Сохранять существующие правила для admin/cpds/staff, в том числе обработку контактов.
- Проверять принадлежность перед сохранением и возвращать обновлённую запись без риска сохранения с последующим отказом при повторном чтении. Ошибочные или запрещённые запросы не должны частично изменять данные.

## Risks / Trade-offs

- [Неполная или некорректная привязка института к подразделению] → запрещать запись при отсутствии однозначного доступного дерева и покрыть тестами общий родитель и несколько уровней.
- [Регрессия существующих полномочий или других API] → ограничить новую политику записью institute_validator и добавить регрессионные тесты.
- [Пользователь без подразделения недоступен] → это согласованное ограничение; исправление выполняют существующие привилегированные роли.

## Migration Plan

Миграция данных не требуется. Развернуть изменение приложения и документации; при откате прежняя политика вновь запретит PATCH ответственным институтов, сохранив уже выполненные изменения данных.
