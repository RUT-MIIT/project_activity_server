# Design

## Context

В `config/settings.py` ключ сейчас задан строковым литералом; `load_dotenv()` вызывается, но не влияет на `SECRET_KEY`. SimpleJWT использует Django `SECRET_KEY` по умолчанию, привязывает токен к числовому `user_id` и выдаёт access-токены на 100 лет. `deploy.sh` записывает тот же литерал в `.env` и перезаписывает существующий файл при повторном запуске. `.env` исключён из Git.

## Goals / Non-Goals

**Goals:**
- Исключить фиксированный ключ из исходников и сценария развёртывания.
- Обеспечить явный отказ запуска без секрета.
- Позволить оператору сменить ключ в окружении и тем самым аннулировать ранее выданные JWT.

**Non-Goals:**
- Изменение срока жизни JWT, схемы идентификации пользователя или фронтенда.
- Автоматическая ротация ключа на каждом развёртывании.

## Decisions

1. В `config/settings.py` читать `SECRET_KEY` из `os.environ` после `load_dotenv()` и выдавать ошибку конфигурации при отсутствующем или пустом значении. Не задавать fallback: иначе ошибка конфигурации может сохранить старый ключ незаметно. `SIGNING_KEY` SimpleJWT отдельно не настраивать, чтобы он следовал актуальному Django `SECRET_KEY`.
2. Убрать секретный литерал из `deploy.sh`. Для существующего `.env` сохранять файл и требовать заданный ключ; для нового развёртывания создавать отдельный случайный ключ криптографическим генератором и записывать его в `.env` с доступом только владельца. Не печатать значение в логах. Альтернатива — требовать ручного ввода при каждом новом развёртывании — создаёт больше шансов на повторное использование или слабый ключ.
3. Описать в `docs/manual_deploy.md` ротацию продакшен-ключа: создать новый уникальный секрет вне репозитория, заменить значение в окружении или `.env`, перезапустить все процессы Django и проверить, что старый токен отклоняется. Новые установки получают новый ключ автоматически; существующие установки требуют намеренной ротации, чтобы не разлогинить людей при обычном развёртывании.

## Risks / Trade-offs

- Секрет отсутствует в локальной и тестовой среде → запуск теперь завершается; настроить тестовое значение через окружение запуска/CI, без общего секрета в коде.
- Смена ключа завершает все JWT-сессии → выбрать время развёртывания и предупредить пользователей о повторном входе.
- Старые токены продолжат работать, если на продакшене оставить прежнее значение в `.env` → выполнить отдельную ротацию и проверить отказ старого токена.
- Публично известный прежний ключ останется в истории Git → ротация обязательна; удаление истории не требуется для аннулирования токенов.

## Migration Plan

1. Перед выкладкой убедиться, что у каждого процесса и тестовой среды задан `SECRET_KEY`.
2. Развернуть код, заменить продакшен-ключ новым уникальным значением и перезапустить все процессы Django согласованно.
3. Проверить: новый вход работает; токен, выданный до ротации, получает отказ на защищённом endpoint; `.env` не попал в Git и его значение не выводится в лог.
4. При откате кода не возвращать старый ключ. Сохранить новый ключ в окружении; если все процессы должны принять единое значение, повторно перезапустить их с ним.
