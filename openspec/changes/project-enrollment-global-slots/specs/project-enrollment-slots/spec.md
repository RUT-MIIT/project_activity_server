# Spec Delta

## Purpose

Определяет глобальную квоту команд на проектную заявку (`recommended_teams_count`) при отображении витрины и при записи команды капитаном или наставником, независимо от того, в скольких треках числится заявка.

## ADDED Requirements

### Requirement: Глобальный счётчик занятых слотов на заявке

Система SHALL считать число занятых слотов на проектной заявке как количество записей `TeamSemester` с данным `project_application`, **без** фильтрации по `project_track`. Счётчик MAY дополнительно ограничиваться семестром заявки/команды, если это нужно для изоляции данных, но MUST NOT делить квоту по трекам.

Система MUST использовать этот счётчик:

- в ответе списка проектов витрины (студенческой и наставнической) в поле занятых слотов (`enrolledTeamsCount` / эквивалент);
- в ответе detail проекта (`enrolled_teams_count` / эквивалент);
- при вычислении `can_enroll` для капитана.

Имена полей API MUST NOT меняться только ради этого change: меняется семантика счётчика.

#### Scenario: Одна заявка в двух треках — общий enrolled

- **WHEN** заявка с `recommended_teams_count = 3` входит в два трека, и на неё уже записаны 2 команды из первого трека и 1 команда из второго
- **THEN** в list/detail любого доступного трека система отдаёт `enrolled_* = 3` (не 2 и не 1)

#### Scenario: can_enroll false при заполненной глобальной квоте

- **WHEN** глобально `enrolled >= recommended_teams_count`, капитан собрал команду `assembled` без проекта, регистрация открыта, и проект доступен группе
- **THEN** detail отдаёт `can_enroll = false`

### Requirement: Запись капитана уважает глобальную квоту

Система MUST при записи команды капитаном на проект отклонять операцию, если число уже записанных на эту заявку команд (глобально) больше или равно `recommended_teams_count` заявки.

Система MUST блокировать конкурентные записи так, чтобы две параллельные попытки не превышали квоту заявки (а не квоту «на трек»).

#### Scenario: Вторая запись с другого трека при rec=1 отклоняется

- **WHEN** заявка с `recommended_teams_count = 1` связана с треками A и B, команда трека A уже записана на заявку, и капитан команды трека B (той же или другой группы с доступом к заявке) пытается записаться
- **THEN** система отклоняет запись с ошибкой о максимальном числе команд

#### Scenario: Последний свободный глобальный слот

- **WHEN** `recommended_teams_count = 2` и глобально уже записана 1 команда (в любом треке)
- **THEN** капитан другой команды успешно записывается, а следующая попытка любой команды на эту заявку отклоняется

### Requirement: Запись наставника уважает ту же глобальную квоту

Система MUST при записи или смене проекта наставником (`enroll-project`) применять ту же глобальную квоту заявки, что и для капитана: отказ, если занятых слотов (исключая текущую команду при смене на тот же проект) уже `>= recommended_teams_count`.

#### Scenario: Наставник не обходит квоту через другой трек

- **WHEN** на заявку с `recommended_teams_count = 1` уже записана команда из трека A, и наставник пытается записать команду трека B на ту же заявку
- **THEN** система отклоняет операцию с ошибкой о максимальном числе команд

#### Scenario: Смена на тот же проект не занимает второй слот

- **WHEN** команда уже записана на заявку X, и наставник повторно вызывает enroll на X (тот же трек/проект)
- **THEN** система не считает это новой занятостью слота и завершает операцию успешно (идемпотентно / без ошибки квоты)

### Requirement: Перелимиченные заявки не откатываются автоматически

Система MUST NOT в рамках этой capability автоматически отвязывать команды от заявок, где текущий `enrolled` уже превышает `recommended_teams_count`. Такие заявки остаются как есть; новые записи сверх квоты MUST блокироваться.

#### Scenario: Уже переполненная заявка блокирует только новые записи

- **WHEN** на заявке с `recommended_teams_count = 3` уже числится 10 команд
- **THEN** существующие привязки сохраняются, а любая новая попытка записи капитана или наставника на эту заявку отклоняется
